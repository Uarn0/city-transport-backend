**Проєкт:** CityTransport (Е-квиток для громадського транспорту з QR-кодом)  
**Компонент:** Backend API Core Services & Controllers

## 1. Опис та критерії приймання користувацьких історій (User Stories)

Для тест-дизайну обрано 4 ключові історії користувача з беклогу, які містять розрахункову та валідаційну бізнес-логіку:

### US-01: Розрахунок вартості замовлення та купівля квитка
* **Jira ID:** `DU-23-19` (Purchase Service & API)
* **Роль:** Пасажир (Авторизований користувач)
* **Опис:** Як пасажир, я хочу обрати тариф, маршрут (опційно) та вказати кількість квитків, щоб система автоматично розрахувала підсумкову вартість замовлення (`TotalAmount`) та згенерувала платіжне посилання.
* **Критерії приймання (Acceptance Criteria):**
  * `AC-01.1:` Загальна вартість розраховується за формулою: $TotalAmount = Price \times Quantity$.
  * `AC-01.2:` Тариф повинен існувати в базі даних та бути активним (`IsActive == true`). Якщо тариф неактивний, повертається `400 Bad Request` з повідомленням про неактивність.
  * `AC-01.3:` Якщо вказано ідентифікатор маршруту (`RouteId`), маршрут повинен існувати в БД. Якщо тариф містить список прив'язаних маршрутів (`tariff.Routes.Any()`), обраний маршрут зобов'язаний входити до цього списку, інакше повертається `400 Bad Request`.
  * `AC-01.4:` Кількість квитків у разовому замовленні (`Quantity`) повинна бути цілим числом у діапазоні від $1$ до $10$ включно.
  * `AC-01.5:` Замовлення створюється у статусі `Pending` з актуальним UTC-таймстампом.

### US-02: Криптографічна генерація та верифікація QR-коду квитка
* **Jira ID:** `DU-23-28` (Ticket Cryptographic Verification)
* **Роль:** Контролер / Водій
* **Опис:** Як контролер або водій, я хочу просканувати зашифрований QR-код квитка пасажира через ендпоінт `POST /api/Tickets/verify`, щоб перевірити його справжність, строк дії, актуальний статус та погасити квиток при першій валідації.
* **Критерії приймання (Acceptance Criteria):**
  * `AC-02.1:` Пейлоад QR-коду розшифровується за алгоритмом AES-256 (перші 16 байт — вектор ініціалізації IV, решта — шифротекст). Розшифрований рядок має формат `{ticketGuid}|{isoUtcTimestamp}`.
  * `AC-02.2:` Якщо шифротекст пошкоджено, підроблено або довжина масиву байтів $< 16$, повертається `IsValid = false`, повідомлення *"Недійсний або підроблений QR-код"*.
  * `AC-02.3:` Якщо квиток із розшифрованим `ticketGuid` відсутній у базі даних, повертається `IsValid = false`, повідомлення *"Квиток не знайдено в системі"*.
  * `AC-02.4:` Якщо поточний UTC-час перевищує `ValidUntil` квитка, статус автоматично змінюється на `Expired`, квиток зберігається в БД, а відповідь повертає `IsValid = false`, повідомлення *"Термін дії квитка вичерпано"*.
  * `AC-02.5:` Якщо квиток вже має статус `Used`, повертається `IsValid = false`, повідомлення *"Цей квиток вже був використаний раніше!"* (захист від повторного проходу).
  * `AC-02.6:` Якщо квиток має статус `Active` і строк дії не вичерпано, статус змінюється на `Used`, фіксуються зміни в БД, повертається `IsValid = true`, повідомлення *"Квиток успішно перевірено та погашено!"* та дані про тариф і маршрут.

### US-03: Логіка правил часових вікон пересадок (Transfer Window Logic)
* **Jira ID:** `DU-23-30` (Transfers & Intermodal Transit Rules)
* **Роль:** Пасажир / Валідатор бортового терміналу
* **Опис:** Як пасажир, який придбав квиток із можливістю пересадки (наприклад, разовий квиток із часовим вікном `DurationMinutes = 60`), я хочу мати можливість здійснити пересадку на інший маршрут у межах часового вікна без додаткової оплати.
* **Критерії приймання (Acceptance Criteria):**
  * `AC-03.1:` Часове вікно пересадки розраховується від моменту оплати/первинної активації: $ValidUntil = PurchasedAt + DurationMinutes$.
  * `AC-03.2:` Якщо валідація на іншому маршруті відбувається в момент $t_{scan} \le ValidUntil$, система фіксує успішну пересадку (Transfer Allowed).
  * `AC-03.3:` Якщо $t_{scan} > ValidUntil$, система блокує пересадку як прострочену та вимагає придбання нового квитка.
  * `AC-03.4:` У разі фіксованої пересадки повторна валідація на тому ж самому транспортному засобі протягом перших 2 хвилин трактується як випадкове подвійне прикладання (Double Tap Prevention) і не викликає помилки.

### US-04: Валідація ліміту поїздок, студентських пільг та правил знижок
* **Jira ID:** `DU-23-35` (Loyalty Discounts & Student Concession Tariffs)
* **Роль:** Пільговий пасажир (Студент / Учень)
* **Опис:** Як користувач зі статусом «Студент», я хочу мати можливість купувати квитки за пільговим тарифом зі знижкою 50% від стандартної вартості (7.50 грн замість 15.00 грн).
* **Критерії приймання (Acceptance Criteria):**
  * `AC-04.1:` При купівлі студентського тарифу (`Price = 7.50m`) загальна вартість розраховується коректно: $TotalAmount = 7.50 \times Quantity$.
  * `AC-04.2:` Неавторизований або непідтверджений користувач без студентського статусу не може оформити пільговий квиток.
  * `AC-04.3:` Максимальний ліміт квитків на одне замовлення зі знижкою обмежений 5 одиницями для запобігання перепродажу.

## 3. Аналіз класів еквівалентності та граничних значень (EP & BVA)

### Параметр 1: Часове вікно дії квитка / пересадки
* **Сутність/Поле:** `Ticket.ValidUntil` відносно часу верифікації $t_{scan}$.
* **Умова:** Разовий квиток дійсний протягом фіксованого вікна $T = DurationMinutes = 60$ хв від моменту купівлі ($t_{purchase}$).
* **Різниця часу:** $\Delta t = t_{scan} - t_{purchase}$ (у хвилинах).

#### Класи еквівалентності (Equivalence Partitioning):

| Клас еквівалентності | Діапазон значень $\Delta t$ | Стан квитка | Очікувана поведінка системи |
| :--- | :--- | :--- | :--- |
| **Клас 1 (Невалідний / Аномальний)** | $\Delta t < 0$ хв (час сканування раніше часу покупки) | Неможливий стан (розсинхронізація годинників або фальсифікація) | Відхилення (Error/Invalid): сканування не зараховується |
| **Клас 2 (Валідний / Активний)** | $0 \le \Delta t < 60$ хв | `TicketStatus.Active`, строк не минув | `IsValid = true`, квиток успішно валідується та погашається |
| **Клас 3 (Невалідний / Прострочений)** | $\Delta t \ge 60$ хв | `TicketStatus.Expired` | `IsValid = false`, статус змінюється на `Expired` |

#### Граничні значення (Boundary Value Analysis — BVA):

| Тестова точка | Точне значення $\Delta t$ | Опис границі | Очікуваний результат |
| :--- | :--- | :--- | :--- |
| **ГЗ-01** | $-1$ секунда ($-0.016$ хв) | Трохи нижче моменту купівлі | Помилка перевірки (Невалідний) |
| **ГЗ-02** | $0$ секунд ($0$ хв) | Момент придбання квитка (Нижня межа дії) | **Валідний (`IsValid = true`)** |
| **ГЗ-03** | $+1$ секунда ($+0.016$ хв) | Одразу після створення | **Валідний (`IsValid = true`)** |
| **ГЗ-04** | $59$ хв $59$ сек ($59.983$ хв) | За 1 секунду до завершення вікна пересадки | **Валідний (`IsValid = true`)** |
| **ГЗ-05** | $60$ хв $00$ сек ($60.00$ хв) | Точний момент завершення терміну дії (`ValidUntil`) | **Невалідний (`Expired`, `IsValid = false`)** |
| **ГЗ-06** | $60$ хв $01$ сек ($60.016$ хв) | На 1 секунду пізніше завершення вікна | **Невалідний (`Expired`, `IsValid = false`)** |

### Параметр 2: Кількість квитків у разовому замовленні (`Quantity`)
* **Сутність/Поле:** `CreatePurchaseRequestDto.Quantity` $\in \mathbb{Z}$.
* **Бізнес-правило:** Разова покупка дозволяє придбати від $1$ до $10$ квитків. Вартість: $TotalAmount = Price \times Quantity$.

#### Класи еквівалентності (Equivalence Partitioning):

| Клас еквівалентності | Діапазон значень `Quantity` | Тип вхідних даних | Очікувана поведінка системи |
| :--- | :--- | :--- | :--- |
| **Клас 1 (Невалідний)** | $Quantity \le 0$ | Від'ємні числа та нуль | Помилка валідації `400 Bad Request` |
| **Клас 2 (Валідний)** | $1 \le Quantity \le 10$ | Допустима кількість одиниць | Успішне створення замовлення `201 Created`, точний розрахунок `TotalAmount` |
| **Клас 3 (Невалідний)** | $Quantity > 10$ | Перевищення дозволеного ліміту | Помилка валідації `400 Bad Request` (перевищено ліміт) |
| **Клас 4 (Невалідний тип)** | Неціле число / рядок | Дробові або некоректні типи | Помилка десеріалізації JSON `400 Bad Request` |

#### Граничні значення (Boundary Value Analysis — BVA):

| Тестова точка | Значення `Quantity` | Опис границі | Очікуваний результат |
| :--- | :--- | :--- | :--- |
| **ГЗ-07** | $-1$ | Від'ємне значення | Помилка 400 Bad Request |
| **ГЗ-08** | $0$ | Ліва зовнішня границя (нуль) | Помилка 400 Bad Request |
| **ГЗ-09** | $1$ | **Нижня внутрішня границя (мінімум покупки)** | **Успіх (TotalAmount = $1 \times Price$)** |
| **ГЗ-10** | $2$ | Нормальне допустиме значення | **Успіх (TotalAmount = $2 \times Price$)** |
| **ГЗ-11** | $9$ | Передмаксимальне допустиме значення | **Успіх (TotalAmount = $9 \times Price$)** |
| **ГЗ-12** | $10$ | **Верхня внутрішня границя (максимум покупки)** | **Успіх (TotalAmount = $10 \times Price$)** |
| **ГЗ-13** | $11$ | Права зовнішня границя (перевищення на 1) | Помилка 400 Bad Request |

### Параметр 3 (Додатковий): Довжина ключа симетричного шифрування AES-256 (`EncryptionKey`)

* **Вимога криптографії:** Довжина симетричного ключа для стандарту AES-256 повинна бути рівно $32$ байти ($32$ символи ASCII/UTF-8).
